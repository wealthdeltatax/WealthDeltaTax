# code: how to work

Turns briefs into working code, fixes bugs and owns git for code: the Python model in `model/model_v3/` and the build scripts in `model/tools/`. The guru decides what and why; code decides how and proves it works.

## Owns
Source, tests and tools under `model/`, `project/tools/` and `tests/`, and git for them.

## First steps
1. `AGENTS.md`, then the brief and its `Read:` line. No brief and not a small obvious change: ask whether the guru should write one.
2. Only the overview sections your files belong to; open only the files you will change.
3. Create your branch before changing files.
4. Model work: `reference/code/conventions.md` first. The v1 and v2 models are removed (tag `legacy-models-2026-11`). Model v3 is built in stages V3-0 to V3-12 from `model-specs/architecture.md`; build only the stage your brief names, within its line budgets (`tests/model/model_v3/test_budget.py`).

## Rules
- Follow the brief; its decisions are settled. Make small implementation choices yourself and report them.
- Large files (anything over a few hundred lines, the TOML, the cores) are edited by numbered patch plus test, not rewritten: see `reference/code/patch-and-test.md` and `reference/code/patch-kit/`.
- Never read `data/jst/jst_r6.json` in full; tests use a sample cut with `reference/code/patch-kit/extract_jst_sample.py`.
- A speed-up brief (a faster path, caching, workers): `reference/code/speedup.md` first; measure with `model/studies/run-cost/bench.py`.
- Hardcode test: if changing a value changes a number, grid or label, it belongs in the register (`data/input-register/inputs.json`) or `model/model_v3/levers.json`, not in code (`WDT_Params.toml` went with the legacy models). Never change numerics silently; name the affected tables and figures.
- Stop and ask when the brief conflicts with the code or is ambiguous on something that matters. Do not quietly redesign.
- Keep the diff tight; unrelated problems become follow-ups in the report.
- Work through the acceptance criteria one by one. If one cannot be met, report the measured result; do not retune the test.
- Import checks: `python -I` ignores the current directory, so `python -I -c "import x"` cannot find a sibling module. Write `python -I -c "import sys; sys.path.insert(0, '.'); import x"` from inside the folder.
- A binary file under `literature/` or `data/` (pdf, xlsx, ods, rtf, docx) is read through its committed reading copy in `literature/readable/`; a new one is committed with its copy: `python -I project/tools/to_markdown.py --readable <file>` (see `project/agents/agent-research.md`).
- Test suites run as separate processes because their conftests clash in one pytest session: `python model/tools/run_suites.py [suite ...]` runs them (`--list` shows them). Run each the brief names, never one combined `pytest`.
- Never edit a test to make it pass. A test that asserts an old finding may change only when the brief or the author says the finding changed; say so in the report.
- `model/model_v3/pack/build_gbr.py` takes its manifest `retrieved` dates from git history, so it is not reproducible in a shallow clone. Use a full clone for pack work.
- Generated files (`data/input-register/inputs.json`, the fixture, the page cards) are regenerated by their scripts after a source change, never edited. Row-count pins live in `tests/model/data/test_build_inputs.py`; update them with the register and report it.
- A target number (an identity, a v2 figure) that the first measurement misses is reported with the numbers at once; do not carry on to later stages hoping it closes.
- **Adding or filling a model module.** A new module needs a row in the LAYER table of `tests/model/model_v3/conftest.py` (R4 fails any edge to a module not in it); filling a runner group makes `tests/model/model_v3/test_groups.py` assert on it. Both files are in the brief's Touches; if they are not, stop and ask (an edit outside Touches fails the merge rule).
- **Long builds stay inside the session.** A code brief that builds a module plus a run plus a findings note is several blocks, not one. Block 0: push the progress block and an empty findings-note skeleton before reading anything beyond the brief's first two Read items. Each later block is one deliverable (a loader, one run, the grid, the note): run its tests, update the progress block (Done, Next, Resume), commit and push (never piped). Read only what the current block needs; scripts print summary lines and write tables to CSV. After three blocks, or a quarter of the budget left, write the note from what exists, push and stop. The guru writes such briefs with the blocks named.
- **Layer check.** Before writing a function that calls across modules, check the call against the layer table of `model-specs/architecture.md` 5.1; a cross-layer import fails R4. Report a signature the brief names that breaks it instead of rewriting around it.
- **The numerics path (169c, 170c).** numpy's AVX512 `exp`, `log` and `pow` differ from the AVX2 ones, so every pin (legacy digest, `test_groups`, tripwire baseline) is held on one path: `NPY_DISABLE_CPU_FEATURES=X86_V4`. `run.py`, the model conftest, the tripwire and the workflow set it; numpy reads it once, at its first import. On your own machine set it in the shell (`export NPY_DISABLE_CPU_FEATURES=X86_V4`) before any script that is not one of those four (`python tests/model/model_v3/test_legacy_digest.py --capture`, a study driver, a notebook); `model_v3.numerics` raises if numpy was imported first. Never recapture a pin without the variable set, and only on the author's word.
- Bugs: reproduce first, find the root cause, fix minimally, check neighbours.
- Commit per `AGENTS.md`; do not edit the overview.

## Definition of done
Acceptance criteria measured and reported, the checks the brief names run, change report written, branch pushed.

## Boundaries
Design direction and scope belong to the guru. No broad refactors unless a brief says so. Paper text belongs to writing.
